## 0. 結論（先に読む）

1. **最優先は「Pi ごと止まったことに外から気づけない」状態の解消。**
   `HEARTBEAT_URL` は未設定のまま（`scripts/health_check.py` が ⏸ を返している）。
   入れない判断（Issue #12、2026-10-19）の根拠の一つは #21 のメモリ上限だったが、
   その上限は 10-24 に**効いていなかった**と判明しており、その後も記録なしの再起動が5日で3回起きている。
   設定は `.env` の1行と healthchecks.io 側の check 作成だけで済む。→ [§1 R-02](#r-02)、[§4 D-1](#d-1)
2. **バックアップは全部 Pi 本体の SD カードの中にある。** 日次 DB も週次スナップショットも同じ媒体に置かれ、
   crontab はどこにも保存されていない。SD が壊れた場合の復旧経路は、現状では成立しない。→ [§1 R-07](#r-07)、[§3](#3-バックアップ復元チェックリスト)
3. **トイレの転倒検知（#20）は、トイレ内部に人感センサーを足す前提でのみ再設計できる。**
   ドアだけで在室を推定する案は既に実データで否定されている。§2 に、浴室見守り（`BathMonitor`）と
   同じ骨格で「在室タイマー」を作る案をまとめた。ただし #20 では B 案（現状維持）が採用済みで、
   A 案（センサー追加）を採るかは利用者の判断待ち。→ [§2](#2-20-トイレ転倒検知の再設計案在室タイマー方式)、[§4 D-2](#d-2)
4. 次回の現地訪問でしかできない作業が上位に固まっている（電池交換・電源確認・センサー位置・センサー追加）。
   訪問前に、ソフト側だけで閉じられる3件（死活監視・オフサイトバックアップ・復元リハーサル）を片付けておくのが効率がよい。

### 対応方針（優先度 S / A）

**R-02 外部死活監視** — #12 の判断を見直し、HANDOFF「外部死活監視」節の手順どおり healthchecks.io を設定する。
#12 の完了条件（意図的に止めたときに通知が届く）まで確認する。通知先に家族1名を入れる案（#12 本文）も同時に決める。
見直す理由は §4 D-1。

**R-05 脱衣所センサー電池** — 次回現地で CR2032 を交換する（#31 のチェックリスト）。
訪問が先になる場合、家族に交換を依頼できるか検討する（手順書の有無は未確認）。

**R-07 バックアップの単一媒体集中** — 方針は「Pi の外に1世代以上」。
最小構成は週次スナップショットを Tailscale 経由で開発者PCへ取り寄せる運用【推測: 具体的な転送手段は未決】。
あわせて **crontab の写しをスナップショットに含める**（現状 `system_snapshot.sh` の対象外で、
内容は #19 のコメントにしか残っていない）。スナップショットには `.env` と生活記録が丸ごと入るため、
転送先でも権限 600 相当と暗号化を維持すること。

**R-03 OOM** — まず `memory_guard.py` の再起動権限が本番に入っているかを確かめる（§4 D-3）。
memory cgroup の有効化（`cmdline.txt` 変更）は起動不能リスクがあるため、現地にいるときに限る（#21 の方針どおり）。
根本原因（iot-monitor が 1GB を超えて育つ理由）の調査は残課題。

**R-04 記録なし再起動** — #30 の「次にやること」のうち、`kernel.panic` / ハードウェア watchdog の設定は
遠隔でできる。電源（公式 27W・直結か）の確認は現地。R-02 が入れば、少なくとも停止時間は計測できるようになる。

**R-01 トイレ転倒** — §2 の再設計案。前提として A 案（内部人感センサー追加）の採否を決める必要がある。

**R-08 復元未実行** — 本番ではなく、バックアップの写しを使ってリハーサルする（§3 の「平時の準備」）。
`restore_db.py` は `--file` で任意パスを指定でき、整合性検証も行うので、別ディレクトリでの試行に使える【推測: 本番以外のパスで動かす際の `ROOT` 固定の扱いは要確認】。

## 2. #20 トイレ転倒検知の再設計案（在室タイマー方式）

### 2.1 前提: ドアセンサーだけでは成立しない

Issue #20 のコメント（2026-09-26）と PROGRESS「わかっている限界」で、次の3案がいずれも実データで否定されている。

| 試した案 | 結果 | 根拠 |
|---|---|---|
| open→close の時間を滞在時間とみなす（現行） | 在室はドアが**閉まっている間**であり、測っている区間が逆 | #20 コメント §1 |
| close→open の時間を在室とみなす | 「在室」と「誰もいないがドアが閉まっている」を区別できない | #20 コメント §2 |
| 短い開閉を通過とみなし入退室を交互に数える | 一度ずれると回復せず、在室時間が現実と合わない | #20 コメント §3, PROGRESS |
| 他のセンサーが静かなことを在室の補助にする | 夜間に誤報が多い | PROGRESS「わかっている限界」 |

したがって本案は **#20 の A 案（トイレ内部に人感センサー T100 を追加）を前提**とする。
B 案（文言変更・現状維持）のままでは、在室タイマーを作っても転倒は検知できない。

### 2.2 方針: `BathMonitor` と同じ骨格を流用する

浴室見守り（`src/bath_monitor.py`）は「ドア閉 → 人感で確定 → 時間監視 → ドア開で終了」を既に実装しており、
状態の DB 永続化と再起動後の復元（`bath_monitor_state` / `restore()`）も入っている。
トイレも同じ形に揃えると、テスト済みの部品と運用知見（Phase1 の誤検知対策など）をそのまま使える。

| 項目 | 浴室（既存） | トイレ（本案） |
|---|---|---|
| 入室の暫定判定 | 浴室ドア close | トイレドア close |
| 確定 | 脱衣所 T100 のモーション（5分以内） | **トイレ内部 T100** のモーション（猶予は実測で決める） |
| 監視する量 | 最後のモーションからの経過 | **ドア閉（入室）からの経過＝在室タイマー**（主）＋最後のモーションからの経過（従） |
| 終了 | 浴室ドア open | トイレドア open |
| 永続化 | `bath_monitor_state` | 同形の `toilet_monitor_state`（新設） |

浴室と違い「最後のモーションからの経過」を主軸にしない理由: 座って静止している間は人感センサーが
反応しにくく、静止時間だけで鳴らすと平常の利用で誤報する【推測: T100 の再検知間隔は文書に記載がなく未計測】。
そこで **在室が続いている時間** を主たる発火条件にし、静止時間は通知文の補足情報と、2段目の判断材料に使う。

### 2.3 状態遷移

```
            ドア close
  [空き] ─────────────▶ [暫定在室]
    ▲                     │  猶予内に内部モーション
    │ 猶予切れ             ▼
    │(無人のまま閉まった) [在室確定] ── 在室タイマー ≥ 閾値1 ──▶ [要確認(1段目通知)]
    │                     │                                     │
    │      ドア open       │ ドア open                           │ 在室タイマー ≥ 閾値2
    └─────────────────────┴─────────────┐                       ▼
                                         │              [要確認(2段目通知)]
                                         ▼                       │
                                   [空き] ◀── ドア open（通知済みなら自動解決を通知）
```

| 状態 | 入る条件 | 出る条件 | 動作 |
|---|---|---|---|
| 空き | 初期状態 / ドア open / 猶予切れ | ドア close | なし |
| 暫定在室 | ドア close | 内部モーション → 在室確定 / 猶予切れ → 空き / ドア open → 空き | 在室開始時刻を記録・永続化 |
| 在室確定 | 猶予内のモーション | ドア open / 閾値1到達 | タイマー監視。モーションごとに最終モーション時刻を更新 |
| 要確認 | 在室タイマーが閾値を超えた | ドア open | 1段目通知 → 閾値2で2段目通知。ドア open で pending を自動クローズし「出てきました」を共有 |

### 2.4 閾値の決め方（シャドー運用）

#20 の「閾値を実データで決める（誤報が出ない値を測ってから）」に従う。

1. センサー設置後、**通知を出さずにログと DB だけに記録する期間**を設ける（期間は2週間程度を想定【推測】）
2. 「在室確定 → ドア open」の時間分布と、在室中のモーション間隔の分布を取る
3. 閾値1は平常の最大値を明確に上回る値、閾値2は閾値1より十分長い値にする。猶予（暫定在室→確定）もここで決める
4. **分布や具体値はリポジトリに書かない。** 生活パターンそのものなので `data/private/` に置く（`docs/WORKFLOW.md`「公開範囲の注意」）

### 2.5 通知の設計

- **カテゴリは新設する**（例: `toilet_no_exit`）。既存の `long_toilet_stay` は家族に「対応不要」で閉じる習慣が
  ついており（#20「影響」）、同じ名前・文面だと新しい通知も無視される
- **`RETROSPECTIVE_CATEGORIES` に入れない。** 事後報告ではなく、今起きていることの通知になるため再通知の対象にする
- **深夜抑制の対象外**（既存の `long_toilet_stay` と同じく緊急扱い）
- **自動解決**: ドア open を観測したら pending を閉じ、「出てきました」を全員に共有する（`BathMonitor` の `on_alert_resolved` と同じ考え方）
- 文面は観測事実だけを書く（「ドアが閉まったまま◯分、中の動きは最後に◯分前」）。転倒と断定しない
- 運用開始時に家族へ「前の通知とは別物で、今度は中にいる間に鳴る」と伝える（#20 のやること）
- 既存の `long_toilet_stay` は、本案の運用開始と同時に止めるか残すかを決める（残すと二重通知になる）

### 2.6 再起動・故障への耐性

記録なしの再起動が続いている（#21, #30）ため、ここを設計の必須要件にする。

| 失敗の仕方 | 対策 | 前例・根拠 |
|---|---|---|
| 在室中にプロセスが再起動して見守りが消える | 状態を `toilet_monitor_state` に永続化し、起動時に復元。古すぎる状態は引き継がない | `bath_monitor.py` の `restore()` / `MAX_RESUME_HOURS`、#19 / #27 |
| 監視タスクが例外で無言停止 | `supervise()` 配下で動かす | `src/task_supervisor.py`、HANDOFF 7/15 |
| 内部センサーの電池切れ | 電池監視の対象に入れ、`BATTERY_IMPACT` に「トイレの見守りが止まる」旨を追加 | #31 |
| 内部センサーが無反応になる | `health_check` のセンサー別しきい値に追加（性質は「使ったときだけ」系） | HANDOFF 2026-09-15 節のしきい値表 |
| ドアセンサーが片側で固着 | 固着ウォッチドッグを流用（open のまま長時間 → 異常扱い） | #14 の固着検知 |
| ドアを閉めずに使う【推測: 実態は未確認】 | ドア open のまま内部モーションが続く状態を別途記録し、シャドー期間に頻度を見て扱いを決める | — |

### 2.7 完了条件（`docs/WORKFLOW.md` の Definition of Done に合わせる）

- 本番に反映され、シャドー期間の実データで在室区間が取れていることを確認した出力がある
- 再起動をまたいだ在室が復元されることを本番ログで確認した
- 意図的なテスト（家族の協力で、ドアを閉めた在室を閾値以上続ける）で通知が届き、ドア open で自動解決した
- 家族に「前の通知との違い」を伝えた

### 2.8 未決事項

- 内部にセンサーを置くことへの本人・家族の受け止め【推測: カメラではなく人感センサーだが、確認は必要】
- 閾値・猶予の具体値（シャドー運用の結果待ち）
- 既存 `long_toilet_stay` の扱い

## 3. バックアップ復元チェックリスト

現状の仕組み（根拠: `scripts/backup_db.sh`, `scripts/system_snapshot.sh`, `scripts/restore_db.py`, #19 コメント）:

| 種類 | 頻度 | 中身 | 保存先 | 保持 |
|---|---|---|---|---|
| DB バックアップ | 毎日 3:00 | `iot.db`（`sqlite3.backup()` 方式） | Pi 内 `data/backup/` | 14日 |
| システムスナップショット | 毎週日曜 4:00 | DB、顔データ、`.env`、systemd unit 3本 ほか | Pi 内 `data/private/system_backups/` | 4週 |

**どちらも Pi の SD カード上にある。** 以下の手順は「Pi は動いていて DB だけ戻したい」場合（A）と
「Pi を作り直す」場合（B）に分けた。B は現状では前提が欠けているため、欠けている箇所を ⚠️ で示す。

### 平時の準備（復元が必要になる前に）
