# 開発の進め方

1人開発 / 本番は遠隔 / 開発者は就活中、という前提に合わせた軽量アジャイル。
教科書どおりのスクラムではなく、**このプロジェクト固有の失敗の仕方**に合わせてある。

## このプロジェクトの敵

機能が終わらないことではなく、**静かに壊れること**。実績:

| 事象 | 気づくまで |
|---|---|
| ドア・モーションセンサーの全滅 | 11日 |
| 家族ダッシュボードの利用停止 | 3週間以上（原因は今も未特定） |
| 外部死活監視の設定漏れ | 3ヶ月（まだ未設定） |
| タブレットが10分おきに500 | 当日中に発見（監査を回していたため） |

どれも「実装が足りない」のではなく「動いているつもりが動いていなかった」。
だからレビューは**チケットの消化率ではなく、本番の実データに対する検証**で行う。

## スプリント

- **長さ: 1週間**
- **ベロシティ・ゼロを正式に認める。** 就活で手が動かない週があるのは想定内。
  ただし**その週も監査だけは回す**（静かな劣化は手を止めている間も進むため）

## バックログ

GitHub Issues。ラベルで優先度と性質を管理する。

| ラベル | 意味 |
|---|---|
| `P0` | 今スプリントで必ずやる |
| `P1` / `P2` / `P3` | 次 / やる / いつか |
| `safety` | 祖母の安全に直結 |
| `silent-failure` | 静かに壊れる系 |
| `ops` | 運用・インフラ |
| `privacy` | プライバシー |
| `course` | 授業の課題 |
| `investigating` | 調査中 |

`safety` と `silent-failure` は優先度ラベルより重く扱う。

## Definition of Done

> **テストが通った ≠ 完了。本番の実データで意図した結果が出ていることを確認して初めて完了。**

2026-09-25 に入れた修正はユニットテストが全部通ったうえで回帰を4件出した。
「同じ失敗パターンが他に何箇所あるか」を grep で数えるまでが修正。

完了の条件:
1. 変更が本番に反映されている（長期稼働プロセスは再起動が要る）
2. 本番の実データで、意図した結果になっていることを確認した出力がある
3. 影響範囲を数えた（同種箇所の件数を出した）
4. コミットされ、push されている

## スプリントレビュー

**マルチエージェントによる本番監査**を回す。問うのは「何を作ったか」ではなく
**「今このシステムは約束を果たしているか」**。

- 領域を分けて並列に点検し、各指摘を**反証役**にかけて確定させる
- 最後に「何が抜けているか」を問う批評役を通す
- 監査済みの領域は次回以降スキップし、未監査の領域に回す

## レトロスペクティブ

気づいた作業上の教訓は**メモリに書き戻す**。
特に「自分の修正が生んだ回帰」は、再発防止のチェックリストとして残す。

## ステークホルダー

- **祖母**: フィードバックを返せない。画面に出るものが正しいかは開発側が保証する
- **家族**: 実質のユーザー。**反応がないこと自体がフィードバック**として扱う
- **祖父**: 現状ほぼ対象外（顔未登録・LINE未登録）

## 公開範囲の注意

リポジトリは public。**実在する高齢者の生活データを扱っている。**
コミット本文・Issue・PR に、特定日の行動時刻や生活パターンを書かない。
具体的な数値が必要な調査結果はローカルの引き継ぎドキュメントに置く。
